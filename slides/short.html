Block 1 · System start-up

Who starts whom at boot

StageWhat it doesWhere you customize it
UEFI firmwareTests hardware, loads the bootloader from the EFI partitionFirmware setup screen, efibootmgr
Shim and GRUBSecure Boot handover, loads kernel and initramfs/etc/default/grub, then sudo update-grub
Linux kernelMemory, CPUs, drivers/etc/modprobe.d/, /etc/sysctl.d/
initramfsTemporary root in RAM that finds the real root/etc/initramfs-tools/
systemd (PID 1)Mounts /etc/fstab, starts services up to graphical.target/etc/systemd/system/, /etc/fstab

Look:

systemd-analyze

systemd-analyze blame

systemd-analyze critical-chain

cat /proc/cmdline

“blame” lists slow units. “critical-chain” shows what actually delayed the boot. They are not the same thing.

Block 2 · Login process

The order of the login files

After your password is accepted

  1. /etc/profile
  2. ~/.profile
  3. /etc/xprofile
  4. ~/.xprofile
  5. /etc/X11/Xsession.d/* (among them: ~/.xsessionrc, the GPG and SSH agents)
  6. cinnamon-session-cinnamon

What to remember

  • LightDM shows the login screen, PAM checks the password, systemd-logind opens the session
  • Changes to these files apply at the next login
  • A syntax error in ~/.profile can break the login. Keep Ctrl+Alt+F3 as a way back

Order read from /usr/sbin/lightdm-session on Mint 22.3.

Block 3 · User access

Why your change “did nothing”

Terminal window in Cinnamon

  • A non-login, interactive shell
  • Reads ~/.bashrc only
  • Inherits the session’s environment

Text console or SSH

  • A login shell
  • Reads /etc/profile, then ~/.profile
  • Mint’s ~/.profile sources ~/.bashrc

Variables and PATH go in ~/.profile. Aliases, prompt and functions go in ~/.bashrc.

Block 3 · User access

Run things automatically: pick the place

Linux can run your commands at different moments. Choose the place that matches when you want it to run.

You want it to run...Use
When you log in to the desktopStartup Applications, or a .desktop file in ~/.config/autostart/
In every terminal you open~/.bashrc
Once per login (variables, PATH)~/.profile
On a schedule, as your usercrontab -e, or a systemd user timer in ~/.config/systemd/user/
On a schedule, for the whole system/etc/cron.d/, /etc/cron.daily/ and the other /etc/cron.* folders
Once at every bootan @reboot line in your crontab, or a systemd unit
At boot, as a background servicea systemd unit in /etc/systemd/system/
When a login shell exits~/.bash_logout

Block 4 · Services and daemons

How systemd starts services

graphical.target

starts LightDM, the login screen

multi-user.target

cron, NetworkManager and the other services

basic.target

sockets, timers and paths

sysinit.target

udev, mounts from /etc/fstab, swap

Services in four facts

  • Each target pulls in the one below it. Start order is bottom first
  • “Enabled” means a symlink in a .wants directory
  • Your overrides go in /etc/systemd/system/, never in /usr/lib/
  • Tray programs are started by the desktop’s autostart, not by systemd

Look:

systemctl list-dependencies graphical.target

systemctl list-unit-files --state=enabled

systemctl list-timers

Block 5 · Network and firewall

What is listening? Read ss -tulpn

A port is only a risk if a program is listening on it. The Local Address column tells you who can connect.

Local addressWho can connectTypical example
127.0.0.1:631 or [::1]:631Only programs on this machinePrinting service (CUPS)
0.0.0.0:5353 or [::]:5353Any machine that can reach youNetwork discovery (mDNS, avahi)
0.0.0.0:22Any machine that can reach youAn SSH server, if you run one

Block 5 · Network and firewall

Firewall: what reaches your ports

A firewall decides which packets may reach your ports. On Mint the front end is ufw, which writes rules for nftables in the kernel. The usual home policy: deny incoming, allow outgoing.

Internet

Network card

Wi-Fi or cable

Firewall

ufw / nftables

Open port

a listening socket

Program

a service

ALLOWED

A reply to a connection you started. The firewall is stateful, so it remembers your outgoing connections.

DROPPED

A new connection from outside to a port that has no allow rule.

A firewall is a second line of defense. It does not replace turning off services you don’t need.

Block 5 · Network and firewall

Docker can go around ufw

When you publish a port (-p 8080:80), Docker writes its own firewall rules. Traffic to that port is forwarded to the container, and a ufw “deny” does not stop it.

Don’t trust “ufw status” alone for containers. Test from another machine. Source: Docker documentation, “Packet filtering and firewalls”.

Block 5 · Network and firewall

Public Wi-Fi checklist (laptop)

On a public network the router is not yours, and strangers share the same local network.

  • Firewall active with deny incoming, and no Docker container published on all addresses
  • Sharing and discovery services off if unused: file sharing, avahi, printing (check with ss)
  • Don’t auto-connect to open networks. Prefer WPA2 or WPA3, or your phone’s hotspot
  • Use a VPN for anything sensitive
  • HTTPS only. Treat a certificate warning as a stop sign
  • Lock the screen when you step away. Turn Bluetooth off if unused
  • Install pending updates before you travel

Block 6 · Hardening, alarms and audit

The weekly ten-minute checkup

Also in the full deck: SSH keys, updates and AppArmor, a desktop alarm for failed logins, and Timeshift.

  • Update Manager: install pending updates
  • ss -tulpn: any listener you can’t explain?
  • sudo ufw status verbose: still active, still deny incoming?
  • sudo docker ps: any container published on 0.0.0.0?
  • last and sudo lastb: any login you don’t recognize?
  • journalctl -p err -b: new errors since last week?
  • Timeshift: is the latest snapshot recent? And the backup of your home folder?
  • ls -l ~/.ssh: permissions still 700 and 600?

Honesty

What was verified, and what was not

Checked on a Linux Mint 22.3 machine

  • File and folder paths, and the Mint menu names
  • The order in which login files are read
  • Defaults: AppArmor on, firewall drops incoming
  • Every look command, with and without sudo, ran without error
  • Examples run for real in a test: the cron line, the systemd timer and the alarm notification

Not verified

  • Commands that change the system were not run: update-grub, update-initramfs, sysctl --system
  • The autostart file at a real login, and a real failed login inside the alarm’s 15-minute window
  • Third-party tools: package names confirmed, the tools themselves not run
  • The key that opens the GRUB menu, and a real WireGuard connection
  • The two VPN services themselves, their price and their terms

One machine is not every machine. Paths and defaults can differ on other editions and versions.
